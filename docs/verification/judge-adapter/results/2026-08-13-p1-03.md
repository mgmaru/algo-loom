## 3. 検証方式

### 3.1. 実サービスの更新と再起動

1. V-10と同じ方式Aの境界で`REVEL_SESSION`を1件だけ取得した。ブラウザからの取得値には期限を補わず、初回事前分類を「認証情報あり・サーバー由来期限不明」とした。
2. 取得値で`GET /settings`を行い、HTTP 200、アカウント識別情報1件、期待値一致を確認した。
3. 初回応答が示した更新候補を、2秒以上空けた次の`GET /settings`で同じ本人アカウントとして再照合した。
4. 本人照合済みの更新候補だけを、現在世代を条件とするKeychain置換で保存し、直後の読戻しが一致することを確認した。
5. Cookie、本人識別値、通常の環境変数を継承しない新規Node.jsプロセスを起動した。新規プロセスはKeychainから保存値と明示期限を読み、期限の事前検査後に`GET /settings`を行って同じ本人を再確認した。
6. 各応答の`Set-Cookie`は、存在、件数、対象Cookie指示件数、変更有無、期限属性の由来へ射影し、生ヘッダーと値を保存しなかった。

更新候補を確認するGET自体も新しい更新指示を返しました。無限に確認を繰り返さず、最初の応答から得て次のGETで本人確認できた値を保存しました。この保存値は、さらに新しい更新指示が返った後でも、新規プロセスから同じ本人の確認に使えました。

### 3.2. ローカルの期限・失効分類

| 固定入力 | 観測した扱い |
|---|---|
| `Set-Cookie`なし | 更新なし、期限不明 |
| 同じ値の`REVEL_SESSION` | 更新指示あり、値変更なし |
| 新しい値と`Expires` | 値変更あり、サーバー由来の明示期限あり |
| 空値または`Max-Age=0` | 明示失効、提出前停止 |
| 期限情報のない既存値 | 期限不明のまま、推測なし |
| 経過済みのサーバー由来期限 | 外部通信前に期限切れとして停止 |
| 世代競合 | 更新競合として提出前停止 |
| 秘密情報保管庫障害 | 保管庫障害として提出前停止 |

固定入力9件はすべて期待結果と一致しました。実際のCookie、応答または期限から派生した値ではありません。

### 3.3. 一時Keychainの障害・競合制御

| 観測 | 結果 |
|---|---|
| 合成レコードの新規保存 | 成功 |
| 同じ項目への重複追加 | 書込障害として分類 |
| 存在しない別項目の読取 | 読取障害として分類 |
| 現在世代を条件とする置換 | 成功 |
| 古い世代を条件とする置換 | 競合として拒否 |
| 競合後の読戻し | 先に成立した値と一致 |
| 障害・競合時の提出ゲート | どちらも提出不許可 |
| 一時Keychain項目の削除 | 成功、削除後の不存在を確認 |

この制御では合成した秘密値だけを使用し、外部通信は0件です。macOSのロック状態またはアクセス制御画面を意図的に変えず、Security Frameworkの失敗終了を同じ保管庫障害分類へ射影できる境界を確認しました。

## 8. 設計へ渡す事実

- 現在のAtCoderは、本人確認用の`GET /settings`に対して3回連続で`REVEL_SESSION`の値を変更する`Set-Cookie`と`Max-Age`を返した。
- 更新候補で同じ本人を確認してからKeychainへ保存し、別プロセスから再利用できる。
- 本人確認の応答自体がさらに更新指示を返すため、「最新の応答値を確認してから保存」を無制限に繰り返す設計にはできない。有限な1回の更新を採用し、確認済みの要求値を保存する境界が必要である。
- 保存した更新値は、その後に別の更新指示を受けた後も新規プロセスで利用できた。約2.3秒、1アカウント、3回のGETによる観測であり、長期利用や複数プロセスでの一般的保証にはしない。
- 期限は`Expires`または`Max-Age`等のサーバー由来属性を出所付きで保持し、ない場合は不明のままにできる。成果物や通常ログに具体的な期限を出す必要はない。
- Keychainの検索条件へ世代を含めることで、先に成立した更新を古い処理が上書きせず、競合として停止できる。
- 秘密情報保管庫の障害は提出機能だけを止め、平文保存へ切り替えない境界を実装できる。
- 本検証はmacOSだけを対象とする。WindowsのOS保護領域とLinux Secret Serviceの原子的更新、ロック、アクセス拒否はMVP完了前の検証マトリクスに残る。
