## ドキュメント概要

この記録は、`p0-08`と`p0-09`で再現したCloudflare検証失敗について、Cloudflare公式トラブルシューティングと現行V-03検証支援コードを照合し、提出なしで原因を切り分けた結果を保持します。

AtCoderへの再接続、ログイン、提出ページへの移動、Cookie取得、Turnstileトークン取得、ソースコード入力、提出POSTは行っていません。ローカルの`data:` URL、Cloudflare公式互換性チェッカー、公開仕様だけを使用しました。

## 0. 結論

`p0-08`と`p0-09`のCloudflare検証失敗について、**現行ヘルパーの`--remote-debugging-pipe`を用いたブラウザ制御方式が主原因**と特定しました。

現行ヘルパーと同じ起動、CDP接続、ターゲット接続、ページ移動をネットワークなしで再現したところ、Chrome 151.0.7922.109は`navigator.webdriver: true`を返しました。Cloudflare公式の[互換性チェッカー](https://browser-compat.turnstile.workers.dev/)は、最初のAutomation Checkで`navigator.webdriver`が真なら自動化ブラウザとして不合格にする実装です。Cloudflareの[対応ブラウザ](https://developers.cloudflare.com/cloudflare-challenges/reference/supported-browsers/)も、自動化ツールは検知され、チャレンジ失敗を生じ得ると説明しています。

対照として、同じ端末、同じ回線、同じChrome、別の空プロファイルを使い、リモートデバッグとCDP接続なしで公式互換性チェッカーを1回実行しました。検証者は実Turnstileを含む`Diagnostics passed`を確認しました。これにより、少なくとも対照実行時点では、ブラウザの基本互換性、JavaScript、拡張機能・キャッシュ、端末時計、Cloudflare到達性、実Turnstileは成立し、ブラウザ制御条件を加えた経路だけが自動化状態になったと区別できます。

AtCoderまたはCloudflareの非公開判定ログ、`p0-09`の6桁エラーコード、Ray IDはありません。このため`p0-09`の一回の失敗について内部ルール名やエラーコードまで断定はしません。一方、現在の`--remote-debugging-pipe`方式がCloudflare公式互換性条件を満たさないことは、ローカル観測、公式チェッカーの判定条件、対照実験が一致しており、方式Aの採否を判断するには十分です。

### 0.1. 判定

| 判定対象 | 結果 | 根拠 |
|---|---|---|
| Cloudflare検証失敗の主原因 | 特定 | 現行ヘルパー相当で`navigator.webdriver: true`。通常起動の対照は公式互換性チェッカー合格 |
| 現行方式AのCDP実装候補 | 不適合 | Cloudflare保護ページを開く前からブラウザがリモート制御状態になる |
| `V-03` | 未実施を維持 | AtCoderへ接続せず、提出POST 0件 |
| `V-04` | 未実施を維持 | 提出IDなし |
| `V-10` | 現行CDP方式は不合格 | 通常ログインを完了できず、原因となる制御条件を特定 |
| MVP実装開始条件 | 未充足 | `V-03`、`V-04`、再設計後の`V-10`が未合格 |

`navigator.webdriver`を隠すフラグ、指紋偽装、stealth設定、ユーザーエージェント変更、Turnstile自動操作等は試していません。これらは原因の除去ではなく自動化状態の秘匿またはBot対策の回避になるため、次の方式候補にしません。

## 1. 調査計画と安全境界

調査は、AtCoderへ失敗を反復する前に次の順序で行いました。

1. Cloudflare公式文書から原因候補とエラー分類を列挙する。
2. `p0-08`、`p0-09`と現行スクリプトを照合し、除外済み条件と未確認条件を分ける。
3. 現行ヘルパーのブラウザ制御条件を、外部通信のない`data:` URLで再現する。
4. Cloudflare公式互換性チェッカーを、リモート制御なしの空プロファイルで1回だけ実行する。
5. 結果が矛盾しない場合だけ原因を確定し、AtCoderへの再接続は行わない。

安全境界は次のとおりです。

- AtCoderへのリクエストと提出を0回にする。
- 既存プロファイル、Cookie DB、パスワード、Cookie、トークン、ヘッダー、生HTMLを読まない。
- CDPの`Network`領域とCookie・Storage取得APIを使わない。
- ローカル診断は`data:` URLだけを対象にする。
- 公式チェッカーの対照は通常起動とし、CDP、開発者ツール、拡張機能を追加しない。
- 通過を目的とする再試行、別回線、プロキシ、VPN、検知抑制設定を使わない。

## 2. 公式情報との照合

### 2.1. Challenge solve issues

Cloudflareの[Challenge solve issues](https://developers.cloudflare.com/cloudflare-challenges/troubleshooting/challenge-solve-issues/)は、失敗候補として不安定なネットワーク、ブラウザ設定・拡張機能、非対応ブラウザ、JavaScript無効、Botらしい動作の誤検知を挙げています。推奨する切り分けは、公式互換性チェッカー、拡張機能無効化、JavaScript有効化、プライベートモード、別ブラウザ・端末、VPN・プロキシ回避、別ネットワークです。

同ページは、Private Access Token要求のHTTP 401は通常のフォールバックであり、それだけでは失敗を意味しないこと、`*.challenges.cloudflare.com`の一部DNS失敗も非致命的であり根本原因として扱わないことを明記しています。この2つは本件の原因候補から除外しました。

### 2.2. 対応ブラウザと自動化

Cloudflareの[対応ブラウザ](https://developers.cloudflare.com/cloudflare-challenges/reference/supported-browsers/)は、次を説明しています。

- Chromeは現行と直前2メジャーバージョンを対応対象とする。
- headlessブラウザとSelenium、Puppeteer、Playwright等の自動化フレームワークは非対応で、チャレンジによりブロックされる。
- 自動化ツールはBot候補として検知され、失敗を生じ得る。
- 開発者ツールはブラウザの動作やデバッグ情報を変え、チャレンジの動作へ影響し得る。

現行コードはこれらのフレームワークを使いませんが、`--remote-debugging-pipe`でChromeをリモート制御し、CDPの`Target.attachToTarget`と`Page.navigate`を実行します。可視ブラウザで人が操作することは、ブラウザがリモート制御状態でないことを意味しません。

### 2.3. `navigator.webdriver`

[W3C WebDriver仕様](https://www.w3.org/TR/webdriver1/#interface)は、ユーザーエージェントがリモート制御下にあるときWebDriver-active flagが真になり、`navigator.webdriver`がその値を返すと定義しています。

Cloudflare公式互換性チェッカーの公開ページは、最初に`navigator.webdriver`を確認します。真なら`Browser is automated (webdriver detected)`として`automated_browser`を設定し、後続診断へ進まず停止します。公式チェッカー自身も、診断対象が自動化フラグ、端末時計、Cloudflareサーバー到達性、実Turnstileであると画面上で説明しています。

### 2.4. エラーコード

Cloudflareの[Turnstileクライアント側エラーコード](https://developers.cloudflare.com/turnstile/troubleshooting/client-side-errors/error-codes/)では、主な分類は次のとおりです。

| コード | 意味 | 本件での扱い |
|---|---|---|
| `110600`、`110620` | チャレンジ・操作タイムアウト | `p0-09`でコード未記録。時計対照は正常 |
| `200100` | 時計または中間キャッシュ | 時計差は公式基準の2分以内。通常対照も合格 |
| `200500` | iframe読み込み失敗 | 通常対照でCloudflare到達性と実Turnstileが合格 |
| `300*`、`600*` | Bot動作を検知した一般的失敗 | 現行制御で`navigator.webdriver: true`のため整合するが、`p0-09`の実コードは未記録 |
| `110100`、`110110`、`110200`、`400020`、`400070` | サイトキー・許可ドメイン等のサイト側設定 | AtCoder側設定を観測しておらず、利用者側で変更しない |

## 3. 実験結果

### 3.1. 実行条件

| 項目 | 条件 |
|---|---|
| OS | macOS 26.5、arm64 |
| Chrome | 151.0.7922.109 |
| [Chrome公式Mac Stable](https://versionhistory.googleapis.com/v1/chrome/platforms/mac/channels/stable/versions) | 調査時点で151.0.7922.138。同一メジャー |
| Node.js | 26系 |
| プロファイル | 実行ごとの空の一時プロファイル |
| システムHTTP・HTTPS・SOCKSプロキシ | 無効 |
| Tailscale | ネットワーク拡張は導入済みだがBackend停止、端末オフライン、Exit Nodeなし |
| AtCoderアクセス | 0回 |
| 提出POST | 0回 |

Chromeは最新パッチより古い`.109`でしたが、Cloudflareの対応単位では現行メジャーです。さらに同じChromeの通常起動対照が公式チェッカーへ合格したため、今回の失敗をこのパッチ差だけでは説明できません。更新は一般的な保守として必要ですが、主原因の修正にはなりません。

### 3.2. 現行ヘルパー相当のローカル再現

[`cloudflare_browser_local_diagnostic.mjs`](../../../../scripts/verification/cloudflare_browser_local_diagnostic.mjs)で、現行[`atcoder_v03_turnstile_probe.mjs`](../../../../scripts/verification/atcoder_v03_turnstile_probe.mjs)と同じ次の条件を再現しました。

- 空の専用`user-data-dir`
- 可視Chrome
- `--remote-debugging-pipe`
- `Browser.getVersion`
- `Target.getTargets`
- `Target.attachToTarget`
- CDPの`Page.navigate`

移動先は外部サイトではなくローカルの`data:` URLです。そこで許可リスト化した3つの真偽値だけを読みました。

| 観測 | 結果 |
|---|---|
| JavaScript実行 | `true` |
| Cookie利用可能 | `true` |
| `navigator.webdriver` | `true` |
| CDP `Network`領域 | 無効 |
| Cookie・Storage読み取り | なし |
| Chrome終了 | 確認 |
| 一時プロファイル削除 | 確認 |

この結果から、JavaScript無効やCookie無効ではなく、ブラウザが標準APIでリモート制御状態を公開していることが分かります。

### 3.3. 通常起動の公式互換性対照

同じ端末と回線で、別の空プロファイルを使い、次の条件でCloudflare公式互換性チェッカーを1回開きました。

- 可視Chrome
- `--remote-debugging-pipe`なし
- CDP接続なし
- 開発者ツールなし
- 利用者追加の拡張機能なし
- 人による画面確認

検証者は`Diagnostics passed`を確認しました。公式チェッカーの4段階はAutomation Check、System Clock、Server Connection、実Turnstileです。したがって通常起動の対照では、少なくともこの4項目が成立しました。

補助確認では、公式チェッカーのサーバー時刻と端末時刻の差は約0.14秒で、チェッカーの失敗基準である2分以内でした。`challenges.cloudflare.com`の診断先にもトランスポート到達できました。これらは通常起動の公式チェッカー合格を補強しますが、ブラウザ内の合格結果を置き換える証拠にはしていません。

対照ブラウザ終了時、対話プロセスへの割り込みにより一時プロファイルが1個残りました。専用Chrome終了、対象パス、所有者、使用中プロセス不在を確認し、その一時プロファイルだけをmacOSのゴミ箱へ移動しました。再利用版の診断スクリプトにはSIGINT・SIGTERM時の子プロセス終了と一時プロファイル削除を追加しました。

## 4. 仮説の評価

| 仮説 | 判定 | 検証結果 |
|---|---|---|
| `--remote-debugging-pipe`を含む現行リモート制御 | 主原因として特定 | 現行相当で`navigator.webdriver: true`、通常対照は公式チェッカー合格 |
| ログイン前の提出防止コード注入 | 原因ではない | `p0-09`で注入を除いても失敗 |
| 別の通常Chromeの同時稼働 | 原因ではない | `p0-09`で全Chrome終了後も失敗 |
| 利用者拡張機能・既存キャッシュ | 原因ではない | 失敗実行と成功対照の両方が空プロファイル |
| JavaScript無効 | 原因ではない | ローカル実行成功、公式チェッカー合格 |
| Cookie無効 | 原因ではない | ローカルで利用可能 |
| 非対応Chromeメジャー | 原因ではない | 現行メジャーで、通常対照が公式チェッカー合格 |
| 最新パッチとの差 | 主原因ではない | `.109`でも通常対照が合格。一般保守として更新余地あり |
| 端末時計のずれ | 原因ではない | 公式基準との差約0.14秒、通常対照合格 |
| システムVPN・プロキシ | 原因ではない | システムプロキシ無効。Tailscale停止、Exit Nodeなし。通常対照合格 |
| Cloudflareへの到達不能 | 原因ではない | 公式チェッカーのServer Connectionと実Turnstileが合格 |
| AtCoder固有WAF・IP評価 | 未観測だが主原因の説明に不要 | サイト所有者側の非公開ルールは観測不能。通常対照は一般Cloudflare環境の証拠 |
| AtCoder側Turnstile設定不備 | 未観測 | サイトキー関連コードなし。利用者側で変更しない |
| PAT要求の401 | 原因候補から除外 | Cloudflare公式が期待されるフォールバックと説明 |
| 一部TurnstileサブドメインのDNS失敗 | 原因候補から除外 | Cloudflare公式が非致命的と説明 |

通常起動対照と現行制御条件の間には、リモートデバッグ以外にも「公式チェッカーとAtCoder」という対象サイトの差があります。ただし、現行制御で得た`navigator.webdriver: true`は公式チェッカーの明示的な不合格条件です。そのためAtCoder固有ルールが別に存在しても、現行方式を合格候補へ戻す理由にはなりません。

## 5. 現行スクリプトとの対応

現行[`atcoder_v03_turnstile_probe.mjs`](../../../../scripts/verification/atcoder_v03_turnstile_probe.mjs)は、Chrome起動直後から次を実行します。

1. `--remote-debugging-pipe`付きでChromeを起動する。
2. `Browser.getVersion`と`Target.getTargets`を送る。
3. ページターゲットへ`Target.attachToTarget`する。
4. `Page.navigate`でAtCoderログインページへ移動する。
5. 人によるログイン完了後だけDOMの限定観測へ進む。

ログイン前のDOM注入、入力自動化、クリック自動化、ネットワーク観測を除いても、手順1〜4でブラウザはリモート制御状態です。`p0-09`の改善は交絡要因を除くうえで有効でしたが、方式の中心に残るリモート制御状態は変えていませんでした。

## 6. `V-03`と方式Aへの影響

### 6.1. 直ちに行わないこと

- 現行ヘルパーでAtCoderログインを再試行しない。
- `navigator.webdriver`を偽装または隠蔽しない。
- `--disable-blink-features=AutomationControlled`、stealth plugin、指紋変更、ユーザーエージェント偽装を追加しない。
- Cloudflare通過を目的にVPN、プロキシ、別回線を反復しない。
- Turnstileトークンを取得、移植、再利用しない。
- V-03の合格条件を「ブラウザで手動提出できた」へ緩めない。

### 6.2. 次の安全な設計作業

方式Aは「可視ブラウザで人が操作する」という条件だけでは不十分です。Cloudflare保護ページを開いている間に、ブラウザをリモート制御状態へしない認証・セッション受け渡し境界へ再設計する必要があります。

候補を検討する場合も、次の順序を維持します。

1. 通常ブラウザ状態を壊さず、既存プロファイルを探索せず、`REVEL_SESSION`だけへ限定できる公式境界があるかを設計レビューする。
2. ブラウザ拡張とNative Messaging等を候補にする場合は、権限、配布、利用者同意、Cloudflare互換性、AtCoderへの説明を別に検証する。採用済みとは扱わない。
3. 新候補をAtCoderへ接続する前に、ローカル信号とCloudflare公式互換性チェッカーで`navigator.webdriver: false`相当と実Turnstile合格を確認する。
4. AtCoderへ説明・確認すべき自動化範囲を整理する。
5. 方式AをBot対策の回避なしに成立させられない場合はP0不合格とし、MVPの提出機能と価値仮説を再検討する。

方式Cで取得したCookieをHTTPクライアントへ渡すだけでは、`p0-07`で観測した提出フォーム内Turnstileを実行できません。したがって原因特定だけで`V-03`を再開可能とは扱いません。
