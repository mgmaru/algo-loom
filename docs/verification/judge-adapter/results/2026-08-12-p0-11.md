## ドキュメント概要

この記録は、`p0-10`で不適合とした`--remote-debugging-pipe`方式を使用しないV-03検証支援コードを作成し、ローカルテストと実行開始条件を確認した結果を保持します。

通常の可視Chrome、利用者による拡張機能の手動読込、ブラウザ内の手動ログイン・Turnstile・提出操作、検証専用拡張と認証付きloopbackの構成へ変更しました。Cookie、CSRFトークン、Turnstileトークンを拡張機能の外へ出さず、AtCoder本体の提出ボタンを自動操作しません。

実サービス検証は、専用Chromeのローカル準備画面で検証専用拡張の手動読込完了を観測できず、AtCoderとCloudflareへ移動する前に中止しました。提出POSTと提出は0件です。

| 現行Chromeでの拡張読込方法 | 手動読込へ確定 | Chrome公式版は137以降`--load-extension`を廃止。公式案内の`chrome://extensions`からの手動読込へ変更 |
| `V-03` | 未実施を維持 | 拡張初期化前に停止し、AtCoderへの移動、ログイン、フォーム準備、承認、提出POST、提出ID取得へ進んでいない |

V-03の合格条件を「ブラウザで手動提出できた」へ変更していません。検証支援コードは、対象・アカウント一致・言語・フォーム構造・ソースコードを確認し、一画面の承認ゲートを通過した後だけAtCoder本体の提出操作を許可し、提出前後の一覧差分または提出詳細URLから提出IDを一意に取得する設計です。

実サービスの合格証拠は得ていないため、コード作成とローカルテスト成功をV-03合格として扱いません。

## 1. 作成した検証経路

### 1.1. 実行スクリプト

[`atcoder_v03_browser_submit.mjs`](../../../../scripts/verification/atcoder_v03_browser_submit.mjs)は次を担当します。

1. リポジトリ外の所有者専用ソースコードと未作成出力パスを検査する。
2. `127.0.0.1`の動的portへ認証付きloopbackサーバーを起動する。
3. 空の一時プロファイルで通常の可視Chromeを起動する。
4. `chrome://extensions`とローカル準備画面だけを最初に開く。
5. ブラウザから受け取るイベントの型、件数、順序、1回制限を検査する。
6. 提出IDを匿名化済み結果では`submission-A`へ置き換え、実際の値をV-04・V-06用の一時状態へだけ保存する。
7. 正常終了、中止、時間上限、SIGINT・SIGTERMでブラウザ、loopback、一時プロファイルを後始末する。

Chrome起動引数には、専用`user-data-dir`、初回画面抑制、同期無効、開始URLだけを使用します。CDP、WebDriver、リモートデバッグのpipe・port、ヘッドレス化、ユーザーエージェント変更、`AutomationControlled`無効化を含みません。

### 1.2. 検証専用拡張

[`atcoder_v03_browser_extension/`](../../../../scripts/verification/atcoder_v03_browser_extension/)はManifest V3の未パッケージ拡張です。

| 境界 | 実装 |
|---|---|
| API権限 | `storage`だけ |
| ホスト権限 | `http://127.0.0.1/*`だけ |
| AtCoderでの実行場所 | `/settings`、対象コンテストの提出ページ、提出結果ページだけ。`/login`では実行しない |
| アカウント | 入力した期待値をブラウザの一時メモリ内で照合し、件数と一致結果だけを返す |
| 認証情報 | Cookie APIを要求せず、Cookie値を読まない |
| フォーム秘密値 | CSRF欄とTurnstile応答欄は件数だけを確認し、値を読まない |
| Turnstile | 利用者が操作する。自動クリック、トークン抽出、移植、再利用をしない |
| 提出 | 対象、言語、ソースコードを設定する。`click()`、`submit()`、`requestSubmit()`を呼ばず、承認後に利用者がAtCoder本体のボタンを押す |
| 提出ID | 提出前の本人一覧1ページと提出後の表示をブラウザ内で比較し、新規候補が1件の場合だけ返す |

`navigator.webdriver`の値はローカル準備画面とAtCoder画面で真偽値だけを確認します。真の場合は隠蔽せず停止します。

### 1.3. loopback境界

- `127.0.0.1`だけへbindし、接続元アドレスと`Host`を固定する。
- 実行ごとに生成した256bit相当のtokenを必要とする。
- tokenはローカルURLのfragmentから拡張機能へ渡し、HTTP要求、AtCoderへのreferrer、結果JSONへ含めない。
- イベントは許可リスト化したキーと型だけを受け付ける。
- `bootstrap_ready`、互換性確認、アカウント確認、フォーム準備、承認、`SEND_STARTED`、`REMOTE_ACCEPTED`の順序を固定する。
- 順序違反、件数違反、自動化信号、アカウント不一致、言語候補の曖昧性、sourceバイト数不一致、Turnstile値読取の申告では停止する。
- `REMOTE_ACCEPTED`後の2件目の提出IDイベントを拒否する。

## 3. Chrome拡張読込方法の修正

### 3.1. 最初のローカル起動

初版は`--load-extension`で検証専用拡張を読み込む設計でした。通常Chromeは起動しましたが、30秒以内に拡張からローカル初期化イベントが届かず停止しました。AtCoder、Cloudflare、Cookie、提出を扱っていません。

Chrome Extensionsチームの[公式案内](https://developer.chrome.com/blog/extension-news-june-2025)と[公式フォーラム告知](https://groups.google.com/a/chromium.org/g/chromium-extensions/c/1-g8EFx2BBY)を確認すると、公式Chromeでは137以降`--load-extension`が廃止されています。非公式の回避フラグ、Chrome for Testing、CDPの拡張読込へ変更しませんでした。Chrome for TestingやCDPはCloudflareの通常ブラウザ互換性を実証する対象にならないためです。

公式案内が示す`chrome://extensions`の「パッケージ化されていない拡張機能を読み込む」手順へ変更しました。専用プロファイルの中だけで利用者が明示操作し、終了時にプロファイルごと削除します。

## 7. 次の実行条件

次回は新しい実行IDを使い、検証者が専用Chromeを操作できる状態で次を一度だけ実施します。

1. `chrome://extensions`で検証専用拡張を手動読込し、ローカル準備画面を1回再読み込みする。
2. ローカルの`navigator.webdriver: false`を機械的に確認する。
3. 同じ専用ChromeでCloudflare公式互換性チェッカーを開き、利用者が`Diagnostics passed`を確認する。
4. AtCoderへ進み、利用者がログインとTurnstileを操作する。拒否時は再試行しない。
5. アカウント、CPython、フォーム、ソースコード、AI設定、自動再送禁止を一画面で確認する。
6. 正確な承認句の後、利用者がAtCoder本体の提出ボタンを1回だけ押す。
7. `submission-A`のID取得可否を確認する。状態不明でも再提出しない。

`p0-01`〜`p0-11`を通じた提出は0件のため、検証全体の1件上限は未消費です。
