## `p0-02`後の設計変更

2026年8月11日に、過去の観測結果を変更せず、方式Cを`V-02`の検証専用経路として許可し、方式AをMVP製品候補として別のP0 `V-10`で検証する方針へ変更しました。正本は[AtCoder認証設計](../../../architecture/atcoder-authentication.md)と[`JudgeAdapter`技術検証計画](../../../project/judge-adapter-verification.md)です。

方式Cによる`V-02`は`p0-04`、`V-05`は`p0-07`で合格しました。`p0-10`でCDPをCloudflare非互換の原因として特定し、`p0-11`で通常ChromeのV-03経路を作成しました。`p0-14`では人によるTurnstileと明示承認後のフォーム`submit`イベントまで到達しましたが、結果ページと提出IDを得られませんでした。`p0-15`で非表示の送信用textareaだけを更新してAceを同期していなかったことを原因として特定し、人によるエディタ往復と送信前ガードを実装しました。`p0-16`で現行DOMに対する過剰なCSS class・祖先関係の条件を修正し、人による提出1件の受理とAtCoder発行の提出IDを取得したため、`V-03`は合格です。`p0-17`では同じ提出IDの最終判定を時刻付きで取得しましたが判定待ちを観測できず、`V-04`は一部観測の未合格です。`p0-18`でV-04の自己検証導線をGoogle Chrome固定の段階式手順へ修正し、`p0-19`で本人照合と最終判定の再取得まで実サービス実行しましたが、既存提出の判定待ちは復元できないため合否を変更していません。`p0-20`でV-04方式Cセッションを提出前に準備し、V-03状態の作成直後からV-04を開始する統合支援コードを実装しました。`p0-21`で提出上限を実サービス検証実行単位へ変更し、この統合再検証の新規提出最大1件を許可しましたが、まだ実行していません。再設計後の`V-10`も未合格であり、P0全体とMVP実装開始条件は未充足です。

## 関連する検証支援コード

[`atcoder_v02_session_check.py`](../../../../scripts/verification/atcoder_v02_session_check.py)は、`p0-04`で記録した方式Cの通信条件と分類を再現するため、実行後に再構成した版です。`p0-04`で使用して削除したファイルとバイト単位で同一とは扱わず、このコードやローカルテストだけを実サービスの証拠にしません。

[`atcoder_v03_submit.py`](../../../../scripts/verification/atcoder_v03_submit.py)は、当日の`V-02`再確認、Cloudflare公式の`cf-mitigated`分類、提出フォーム構造とTurnstile関連付け、`V-05`、提出ゲート、POST上限1回、提出IDの一意な取得を順番に適用する検証支援コードです。`p0-07`では、AtCoder公式JavaScript実行前の問題別・名前なし言語`select`を実サービスで解析し、`V-05`の合格を確認しました。その後の対象フォーム内Turnstile停止条件によりPOSTを呼ぶ経路へは到達していません。`V-05`の合格を`V-03`の合格とは扱いません。

[`atcoder_v03_turnstile_probe.mjs`](../../../../scripts/verification/atcoder_v03_turnstile_probe.mjs)は、空の専用プロファイルと可視Chromeを使い、JavaScript実行後のTurnstile応答欄を値を返さず観測する補助コードです。`p0-08`ではログイン段階で中止したため、実行時応答欄の実サービス証拠は得ていません。実行時版にあったログイン前のページ注入を除く二段階へ実行後に修正しており、現在のコードやローカルテストを`p0-08`の成功証拠にはしません。

修正版を実サービスで使用した`p0-09`でも、ログイン時のCloudflare検証失敗により対象提出ページへ到達しませんでした。ページ注入と既存Chrome同時稼働を除いた事実は保持しますが、Cloudflareの内部理由やブラウザ制御チャネルの寄与は断定しません。現在のコードを、同じ方式の無条件な再試行やBot対策の回避へ使用しません。

[`atcoder_v03_browser_submit.mjs`](../../../../scripts/verification/atcoder_v03_browser_submit.mjs)と[`atcoder_v03_browser_extension/`](../../../../scripts/verification/atcoder_v03_browser_extension/)は、`p0-10`の原因特定後に作成した通常ChromeのV-03経路です。利用者が空の専用プロファイルへ検証専用拡張を手動読込し、ログイン、エディタ切替、Turnstile、AtCoder本体の提出ボタンを操作します。拡張はCookie、CSRFトークン、Turnstileトークンの値を読まず、提出操作を自動化しません。`p0-16`の版は、AtCoder本体の切替操作でAceとプレーンテキスト欄を往復し、戻ってきた`FormData`のソース一致を承認時・送信時に確認します。現行DOMのCSS classや不要な祖先関係には依存せず、一意な要素、対象フォームへの所属、可視モード、直列化値を安全境界とします。実サービスの合格証拠は`p0-16`の匿名化済み実行記録です。

[`atcoder_v04_verdict.py`](../../../../scripts/verification/atcoder_v04_verdict.py)は、V-03の所有者専用一時状態から実際の提出IDをメモリへ読み、本人照合後にそのID1件だけをAtCoderの判定状態経路へ指定します。`p0-18`では推奨入口をGoogle Chrome固定とし、ログイン分岐、DevToolsのCookie対象行、秘密入力、通信承認を段階的に案内するよう修正しました。待機と最終を別の時刻付き観測として保存し、両方を実サービスで観測した場合だけ`V-04`を合格とします。`p0-19`ではこの入口を実サービスで実行し、本人照合と最終判定の再取得まで完了しましたが、判定待ちは未観測のため`V-04`を合格にはしません。
