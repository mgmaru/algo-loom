# JudgeAdapter技術検証の実施手順と成果物

> 対象: [`JudgeAdapter`技術検証計画](../../project/judge-adapter-verification.md)を安全かつ再現可能に実施するための準備と運用
>
> 状態: P0認証再実施済み（停止条件により判定不能）
>
> 作成日: 2026年8月11日
>
> 正本: 検証項目、優先度、合格条件は[`JudgeAdapter`技術検証計画](../../project/judge-adapter-verification.md)を優先する

## ドキュメント概要

本書は、検証の入力を固定する方法、一時データと成果物の分離、外部作用前の停止条件、観測方法、成果物の確定手順を定義します。検証の合格条件やMVPの範囲は変更しません。

## 0. 結論

検証で扱うデータを次の3領域へ分離します。

| 領域 | 置き場所 | 保持 | 内容 |
|---|---|---|---|
| 匿名化済み成果物 | [`results/`](results/) | Gitで保持 | 観測事実、合否、リクエスト集計、初期値候補、設計への反映先 |
| 検証用作業データ | リポジトリ外の一時ディレクトリ | 検証後に破棄 | 仮想環境、使い捨て検証コード、入出力例、提出用ソースコード、一時出力 |
| 認証情報 | 外部ツール用の専用Cookieファイルまたは外部ツールの認証保管先 | 成果物へ移さない | Cookie、セッショントークン、パスワード |

`results/`へ生のコマンド出力を複製しません。必要な値だけを許可リスト方式で転記し、[記録テンプレート](results/run-record-template.md)の機密情報検査を通してから成果物を確定します。

## 1. 準備タスク

| ID | タスク | 依存 | 完了条件 |
|---|---|---|---|
| `T-01` | 検証入力を固定する | なし | 終了済み問題、1言語、1OS、期待するアカウント、提出用ソースコードを決める |
| `T-02` | 当日の外部条件を確認する | `T-01` | AtCoderの一般利用規約、対象コンテストの個別規則、Bot対策の状態を公式情報で確認する |
| `T-03` | 隔離した実行環境を作る | `T-01` | リポジトリ外に仮想環境、作業ディレクトリ、専用Cookieファイルのパスを用意する |
| `T-04` | 観測方法を確認する | `T-03` | 本文・秘密情報を保存せず、時刻、所要時間、状態、欠損、リクエスト数を記録できる |
| `T-05` | 読み取りだけの検証を行う | `T-02`〜`T-04` | `V-02`、`V-01`、`V-05`の順で確認し、提出前停止条件をすべて満たす |
| `T-06` | 1件の提出を承認する | `T-05` | 問題、アカウント、言語、ソースコードのハッシュ、外部作用を人が確認する |
| `T-07` | 提出と判定を確認する | `T-06` | `V-03`、`V-04`、`V-06`、`V-08`を同じ提出IDで確認する |
| `T-08` | 安全な障害確認を行う | `T-07` | `V-07`、`V-09`を確認し、未観測の障害を意図的にAtCoderへ起こさない |
| `T-09` | 成果物を確定する | `T-08` | 匿名化、合否判定、初期値候補、問い合わせ用事実、正本文書への反映候補を記録する |

`T-06`まではAtCoderへの提出を行いません。`T-06`で一つでも確認できない項目がある場合は停止し、提出回数を消費しません。

## 2. 検証入力

実行前に次を決め、成果物の「実行条件」へ記録します。

| 入力 | 選定条件 | 成果物へ残す内容 |
|---|---|---|
| 対象問題 | 終了済みの通常のAlgorithm過去問1件。対話的問題、特殊コンテスト、個別規則が不明な問題を避ける | 正規問題ID、公式URL、終了済みと確認した時刻 |
| 言語 | 正規言語IDを一つだけ選ぶ | 正規言語ID、提出直前に解決したAtCoder固有のID・表示名・処理系・バージョン |
| OS | 実機一つだけ | OS名、バージョン、CPUアーキテクチャ。ホスト名と利用者名は残さない |
| アカウント | 検証者自身が所有する一つのアカウント | 識別情報を取得できた事実と期待値との一致。不必要な場合は実際のユーザー名を残さない |
| ソースコード | 検証者自身が作成し、対象問題へ提出してよいもの | `source-A`等の実行内別名とバイト数。本文、ハッシュ、絶対パス、生出力は残さない |

提出IDは`V-04`と`V-06`が終わるまで一時領域で保持します。成果物では`submission-A`等の実行内別名へ置き換え、公開情報との恒久的な紐付けが必要だと別途判断した場合だけ実際のIDを残します。

## 3. 当日の外部条件

実行日の直前に、少なくとも次を再確認します。

- [AtCoder利用規約](https://atcoder.jp/tos?lang=ja)
- 対象コンテストの公式ルールと終了状態
- [AtCoderのAI学習拒否設定の説明](https://info.atcoder.jp/overview/about/ai-training-opt-out)
- [`online-judge-tools`の公式リポジトリ](https://github.com/online-judge-tools/oj)と[Cloudflare関連Issue](https://github.com/online-judge-tools/oj/issues/934)
- 使用するパッケージの公開版、取得元、ハッシュまたはGitリビジョン

確認したURL、確認時刻、確認結果だけを記録します。規約本文、問題文、Issue本文の複製は成果物へ含めません。

次の場合は検証を開始しません。

- 対象問題が終了済みか判断できない
- 個別規則と一般利用規約の関係を判断できない
- ログインにCAPTCHA、Turnstileその他のBot対策の回避が必要になる
- 他人のCookie、ブラウザCookieの複製、プロキシ切り替え等が必要になる
- 1問だけにアクセスする構成、有限の待機、リクエスト数の計測を保証できない

## 4. 隔離した実行環境

### 4.1. 作業場所

検証用作業データは、`mktemp -d`等で作ったリポジトリ外の一時ディレクトリへ置きます。シェル変数には`ALGOLOOM_VERIFY_ROOT`等のタスク固有名を使い、`HOME`を上書きしません。

一時ディレクトリには所有者だけがアクセスできる権限を設定し、次を同じ配下へ分けます。

```text
<ALGOLOOM_VERIFY_ROOT>/
├── venv/          # 検証専用のPython仮想環境
├── work/          # 入出力例、提出用ソースコード、使い捨て検証コード
├── state/         # 専用Cookieファイル等の外部ツール状態
└── scratch/       # 成果物へ転記する前の一時出力
```

リポジトリ直下の`.verification-work/`も誤操作時の退避先としてGitの対象外にしています。ただし、認証情報は除外設定だけに頼らず、原則としてリポジトリ外へ置きます。

### 4.2. ツールの固定

システムのPython環境へ直接インストールせず、検証専用の仮想環境を使います。実行時には次を記録します。

- Python、`uv`、`online-judge-tools`、`online-judge-api-client`と直接利用するHTTPライブラリのバージョン
- PyPI版なら配布ファイルのバージョンとハッシュ、Git版ならリビジョン
- パッケージ解決結果
- 実行した入口が`oj`、`oj-api`、Python API、使い捨ての薄いラッパーのどれか

`online-judge-tools`のCLIと`online-judge-api-client`の構造化出力は別々に評価します。CLI全体が動作しても、提出ID、アカウント識別情報、判定観測を安定した型で取得できなければ、`JudgeAdapter`の候補実装として無条件に採用しません。

起動時の自動更新確認等、AtCoder以外への通信もリクエスト集計と混同しないよう、送信先別に記録します。

提出一覧を反復する下位APIを使う場合、ページを一つに明示的に制限し、対象の提出IDを見つけた時点で停止します。既定の反復処理へ無制限のページ列を渡さず、過去の提出全体を取得しません。提出IDを指定して一件だけ取得する経路を実証できるかも、`V-04`と`V-06`の採否根拠へ含めます。

## 5. 観測と保存の境界

### 5.1. 記録するもの

- UTCの取得時刻と単調増加時計で測った処理時間
- 操作の入口、終了コード、成功・失敗・状態不明の分類
- 許可リストへ正規化したフィールド名、型、単位、欠損
- HTTPメソッド、送信先の分類、応答状態の分類、リクエスト数、待機時間
- 入出力例の件数と入力・期待出力の対応関係を確認できた事実
- 言語候補数と、一意に解決したID、表示名、処理系、バージョン
- 判定待ちと最終判定の時刻付き観測

### 5.2. 記録しないもの

- Cookie、パスワード、セッショントークン、CSRFトークン、認証用URL
- `Authorization`、`Cookie`、`Set-Cookie`を含む生のHTTPヘッダー
- 問題文、生のHTML、完全なJSON応答、入出力例の実値
- 提出用ソースコード、標準入力、標準出力、標準エラー出力
- 実際のアカウント名、メールアドレス、ホスト名、利用者名、不要な絶対パス
- 外部ツールの生ログ、例外の完全なスタックトレース

`oj-api get-problem --full`のように必要な言語一覧と保存禁止の生HTMLを同じ応答へ含める入口を使う場合、応答全体をファイルへ保存しません。処理中に許可したフィールドだけへ射影し、射影後の値だけを観測記録へ転記します。

## 6. 実行ゲート

### 6.1. 読み取りゲート

次の順に実行し、各操作の間隔とリクエスト数を記録します。

1. 専用Cookieファイルを指定し、提出せずに認証状態とアカウント識別情報を確認する（`V-02`）。
2. 同じ対象問題から公開入出力例だけを取得し、件数と対応関係を確認する（`V-01`）。
3. 対象コンテストで有効な言語一覧から、正規言語IDを一意に解決する（`V-05`）。

次のいずれかに該当したら提出へ進みません。

- アカウント識別情報を取得できない、または期待したアカウントと異なる
- ページ構造の変化と未認証を区別できない
- 入出力例の件数または対応関係を維持できない
- 言語候補が0件または複数件になる
- Bot対策、429応答、外部サービスの拒否を観測した
- 提出後に提出IDを構造化して取り出す経路が事前の静的確認で見つからない

### 6.2. 提出ゲート

AtCoderへ送信する直前に、実行者が次を一画面で確認します。

- 正規問題IDと公式URL
- 取得済みアカウント識別情報が期待値と一致したこと
- 正規言語ID、AtCoder固有の言語ID、表示名、処理系、バージョン
- ソースコードのバイト数とハッシュ。成果物には値を残さない
- この操作が検証全体で唯一の提出であること
- AtCoderのAI学習拒否設定を必要に応じて確認する公式リンク
- 送信開始後に応答が不明でも自動再送しないこと

この確認に対する明示的な承認後だけ`V-03`を実行します。確認を省略する非対話オプションや、提出前待機を無効化するオプションは使用しません。

### 6.3. 提出後

1. 応答から提出IDを取得し、`submission-A`として一時的に関連付けます（`V-03`）。
2. 同じIDだけを使い、判定待ちと最終判定を取得時刻付きで観測します（`V-04`）。
3. 最初のプロセスを終了し、別プロセスから同じIDを再照合します。再提出を呼ぶ経路は使いません（`V-06`）。
4. 返された場合だけジャッジ実行時間とメモリを単位付きで記録し、欠損時は欠損のままにします（`V-08`）。

ポーリングの上限へ達しても提出失敗とは判定しません。提出IDを保持したまま`VERDICT_PENDING`相当として終了し、後から同じIDで再確認します。

## 7. 障害確認

障害の証拠を次の3段階に分けます。

| 証拠 | 意味 | 例 |
|---|---|---|
| 実サービスで観測 | 通常操作中にAtCoderから実際に得た事実 | 未認証、判定待ち、最終判定 |
| ローカルで制御 | AtCoderへ負荷を掛けず、使い捨て検証コードで起こした事実 | 接続失敗、応答遅延、待機指示、形式不正 |
| 静的確認 | 使用ライブラリの公開インターフェースや実装を確認した事実 | 接続とリクエストの上限を別々に指定できるか |

`V-07`と`V-09`のために、AtCoder側の拒否、レート制限、ページ変更、通信障害を意図的に発生させません。空の専用Cookieファイルによる未認証確認と、ローカルの制御可能なHTTP応答を優先します。実際に観測していない状態は、別の障害を根拠に「観測済み」としません。

期限切れセッションを確認するために、使用中のブラウザセッションを複製または破壊しません。安全に用意できない場合は未観測とし、どの例外や応答を分類境界にする予定かを静的確認として分けて記録します。

## 8. 成果物の確定

1. [記録テンプレート](results/run-record-template.md)を同じディレクトリの`YYYY-MM-DD-<run-id>.md`へ複製します。
2. 各検証項目を`未実施`、`合格`、`不合格`、`未観測`、`中止`のいずれかにします。
3. 実サービス、ローカル制御、静的確認の証拠を混ぜずに記録します。
4. P0が一つでも不合格ならMVP実装開始条件を不合格とし、回避実装案ではなく範囲と価値仮説の再検討先を記録します。
5. P1が不合格なら影響する機能と見直す正本文書を記録します。
6. 未決事項2.3の数値は「初期値候補」とし、決定値として書き換えません。
7. 未決事項8.1へ渡すリクエスト数、間隔、保存内容、認証方式を集計します。
8. `online-judge-tools`の採否を`採用候補`、`条件付き`、`不採用`、`判断保留`のいずれかで記録し、CLIと下位APIの根拠を分けます。
9. 一時データを破棄する前に成果物だけで合否の根拠を説明できるか確認します。
10. 機密情報検査後に成果物をGitへ追加します。

成果物の確定後、検証用作業データと専用Cookieファイルを削除します。外部ツールが利用者の通常環境へ作成した認証状態がないかも確認します。削除対象は作成時に記録した一時ディレクトリの正確なパスに限定し、広いパスや未解決の変数を削除対象にしません。

## 10. 事前調査で判明した注意点

2026年8月11日に、AtCoderへ接続せず、パッケージの公開情報、ヘルプ、インストール済みコードだけを確認しました。次は`V-01`〜`V-09`の観測結果ではなく、実行環境を用意するための注意点です。

| 観点 | 確認した事実 | 準備への反映 |
|---|---|---|
| 公開版 | PyPIの`online-judge-tools`最新版は`11.5.1`で、公開日は2021年9月13日 | バージョンだけで現在のAtCoder対応を推測せず、当日に実動を検証する |
| Python 3.12 | `uv`が既定で選んだPython 3.12.13では、`distutils.version`の読み込みに失敗してCLIが起動しなかった | Pythonのバージョンを明示し、AtCoderへ接続する前に全入口の起動確認を行う |
| Python 3.9 | macOS付属のPython 3.9.6ではCLIを起動できたが、現在解決された`urllib3`からTLS実装に関する警告が出た | 直接・間接依存を固定し、TLS警告を無視したまま提出へ進まない |
| 自動通信 | `oj --version`の実行時にもPyPIへの更新確認が発生した | AtCoder以外への通信を別集計にし、再現に不要な自動通信を識別する |
| 認証確認 | `oj login --check`はログイン済みかを返すが、アカウント識別情報は返さない | `V-02`には、同じセッションから識別情報を安全に抽出する別の検証経路が必要 |
| 提出ID | `oj-api submit-code`の構造化出力は提出URLを持ち、URLから提出IDを得られる設計になっている | `V-03`ではCLIの真偽値ではなく、下位APIの提出結果を確認する |
| 判定確認 | `oj-api`の公開サブコマンドには提出IDを指定する判定取得がなく、Python APIの提出詳細取得は非推奨かつ未実装になっている | `V-04`と`V-06`は無条件に成立するとみなさず、追加の薄い検証コードが必要 |
| 提出一覧 | Python APIの提出一覧反復は、ページ上限を渡さない場合に後続ページを走査し得る | 一ページへ制限し、対象IDを得た時点で停止する。制限できなければ実行しない |
| Bot対策 | 公式リポジトリには、AtCoderのCloudflare導入後にGUIログインが失敗する未解決Issueがある | 回避方法を追加せず、通常の認証経路が失敗したら検証を停止する |

この事前調査だけでは、現在のAtCoderに対するP0の合否は判定しません。

2026年8月11日の`p0-02`では、時間を空けてパスワード入力型CLIの認証を1回再実施しました。標準の認証確認は302のログイン誘導となり、公開ログインページにはTurnstileのマーカーが残っていました。登録直後の反映遅延だったという仮説を支持する観測は得られず、原因を一意に分類できないため停止条件に従って提出せず終了しました。
